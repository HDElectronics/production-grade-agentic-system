Structure

The layers, and why they are separate

The code is split by responsibility. Each layer calls only the ones below it, so the HTTP code never talks to OpenAI and the agent never parses a request.

DirectoryOwnsKnows nothing about
src/interfaceRoutes, auth dependencies, status codesModels, prompts, graph internals
src/agentThe LangGraph graph, prompts, tools, memoryHTTP, tokens
src/servicesModel access: registry, retries, fallbackConversations, users
src/dataTables (SQLModel), request and response schemas, the database serviceThe agent
src/systemLogging, metrics, tracing, rate limits, the Redis clientBusiness logic
src/configOne settings object read from the environmentEverything else

The payoff is replaceability. Swapping OpenAI for another provider touches src/services only; moving off Postgres touches src/data. It also makes testing cheap: the test suite replaces the database with an in-memory fake and the models with scripted doubles, without starting any infrastructure.

Building your own

Draw these boundaries on day one, even when each layer is a single file. The expensive mistake is a route handler that builds prompts and calls the model directly: it can't be tested, traced or reused from a worker or a CLI.

Identity

Users, sessions, and two kinds of token

A user owns many chat sessions, and each session is one LangGraph thread: its id is used as thread_id, so the session is also the key of the conversation history. Authentication follows that shape. Register and login return a user token, which can only manage sessions. POST /auth/session returns a session token, which is the only kind the chat routes accept.

This gives every chat request exactly one conversation, decided by the server rather than by a field the client could change, and it limits the damage of a leaked chat token to one conversation. The two kinds share one JWT format and are told apart by a typ claim that every route checks. Each token also has a random jti; logging out writes that id to Redis until the token would have expired, and every route looks it up.

Trade-off: JWTs avoid a database read to check a signature, but revocation needs a shared store. If Redis is down, the check lets tokens through and logs an error, choosing availability. A system with stricter requirements would refuse the request instead.

Building your own

Decide early what a "conversation" is and make it the unit of authorization. Put the token kind in the token, and give tokens an id from the start; adding revocation later is much harder than adding it to an empty system.

State

Where each kind of state lives

The API processes keep nothing between requests that another process would need. Everything shared is in Postgres or Redis, so you can run several uvicorn workers and several containers behind a load balancer, and restart any of them.

StateStoreLives forWhy there
Users, sessionsPostgres tablesUntil deletedRelational data with unique emails and foreign keys
Conversation historyLangGraph checkpoints (Postgres)Until the session is deletedWritten after every graph step; the thread can be resumed and inspected
Long-term memorymem0 in pgvector (Postgres)Per user, across sessionsRecalled by meaning, through vector similarity
Rate-limit countersRedisSeconds to hoursFast increments with expiry, shared by every worker
Revoked tokensRedis, append-only fileUntil the token expiresRead on every request, must survive a restart
Compiled graph, pools, bound modelsProcess memoryThe processBuilt once, read-only during requests
Request id, trace idA ContextVarOne requestAttached to every log line of that request only

Three kinds of data share one Postgres instance (with the pgvector extension). At this scale that is one backup, one connection string and one thing to monitor. If memory search or checkpoint writes grow large, they are the first to move to their own store.

Building your own

Write this table for your system before writing code. For each piece of state, ask who reads it, for how long, and what happens if it is lost. Anything per-process (a counter, a cache, a "current model" variable) is a bug waiting for your second worker.

Agent

The agent loop: two nodes and a checkpointer

The graph has two nodes. chat calls the model. If the reply asks for tools, it routes to tool_call, which runs them and routes back to chat with the results; otherwise the graph ends. Each node returns a Command that both updates the state and names the next node, so the routing sits next to the logic that decides it.

A hand-written while loop could do the same. LangGraph is used for what comes with the graph: a checkpoint after every step (the history, for free), streaming of model output from inside a node, a recursion limit that stops runaway tool loops, and one span per node in the traces. Because the server holds the history, the client sends only the new turn.

Building your own

Start with this two-node loop and a persistent checkpointer. When you need retrieval, guardrails, or human approval, add them as nodes rather than growing the chat node: each new node gets its own checkpoint, trace span and tests.

Context

Short-term and long-term memory

Short-term memory is the thread itself. Before each model call it is trimmed to the most recent messages that fit in MAX_CONTEXT_TOKENS, starting on a user message so the model never sees a reply without its question. That budget is separate from MAX_TOKENS, which caps the reply, because the two answer different questions: how much the model reads, and how much it may write.

Long-term memory is a set of facts about the user. After each turn, mem0 sends that turn to a small model that extracts facts, embeds them and stores them per user. Before each run, the latest message is used as a search query and the matching facts are written into the system prompt.

The two sides sit differently on the request path. Recall is one vector search, so it runs before the graph and the user waits for it. Writing calls a model, so it runs in a background task after the reply is sent, with only the new turn, so its cost doesn't grow with the conversation. A failed recall returns no facts rather than failing the chat.

Memories belong to the user, not the session: deleting a conversation leaves them in place. That is useful for personalization and a decision you need to make consciously for privacy and data-deletion requests.

Building your own

Keep anything that calls a model off the request path unless the user is waiting for its result. Decide your memory retention and deletion rules before you store the first fact.

Resilience

Calling models: retry, fall back, or fail

Model APIs fail in different ways, and each kind needs a different answer. The LLM service sorts errors before reacting to them:

ErrorResponseReason
429, timeout, connection, 5xxRetry with backoff (3 tries, 2–10 s), then the next modelThe request was fine; the service was busy
404, 403Next model right awayThis model isn't available to this key
400, 401, 422Raise to the callerThe same request fails on every model

Every call starts at the default model and walks the registry once, with a local index. Nothing about one request's failure changes which model the next request uses, and every model in the registry carries the same tools, so a fallback model can still search the web. Latency is recorded per model that answered, and every fallback increments a counter, so a provider slowly degrading shows up on the dashboard before users notice.

Building your own

Classify errors before you add retries: retrying a bad request on five models multiplies cost and delay for nothing. Keep fallback state per call. If you need several providers, budgets or caching, a model gateway can take over this layer; the interface stays the same.

Delivery

Streaming with server-sent events

The streaming endpoint is a POST that answers with text/event-stream. Server-sent events are one-way and plain HTTP, so they pass through load balancers and proxies that WebSockets sometimes don't, and the client reads them with a few lines of code.

LangGraph's messages stream mode emits model output as it is generated, even though the chat node calls the model with a normal ainvoke. It emits everything, including tool results, so the endpoint forwards only text from the chat node and drops reasoning blocks. Once the first byte is sent the HTTP status can no longer change, so a failure mid-stream ends with a frame that carries an error field. The response also tells proxies not to buffer it.

Building your own

Decide what the user is allowed to see before you stream: tool output and model reasoning are easy to leak by accident. Define how errors look inside the stream, and measure the stream's whole duration, not the time to the first byte.

Safety

Protecting the API

A request meets the cheap checks first. The middleware chain adds CORS, a request id and default rate limits; then FastAPI runs the auth dependency, which checks the token's signature before it touches the database; then the body is validated; then the route's own rate limit is counted; only then does the handler run.

  • Rate limits are counted per client IP in Redis, with tighter limits on expensive or abusable routes (chat, register, login). Behind a reverse proxy, FORWARDED_ALLOW_IPS tells uvicorn to trust the proxy's X-Forwarded-For; without it every user shares the proxy's address.
  • Input is validated by type: clients may send only user and assistant messages of up to 3000 characters. The system prompt is built on the server, which removes one easy route for prompt injection.
  • Errors return a stable message and the response's X-Request-ID; the cause goes to the logs under that id, never to the client.
  • Secrets are required: the app refuses to start without a JWT secret (or, outside development, with one shorter than 32 characters), and compose refuses to start without the JWT secret and Grafana's admin password. Data stores listen on localhost only.
Building your own

Order checks from cheapest to most expensive, and rate-limit before any model call. For authenticated routes, consider limiting per user instead of per IP. Make missing secrets a startup error, never a default.

Observability

Seeing what happens: four signals

SignalToolAnswers
MetricsPrometheus, GrafanaHow many, how fast, how often a model falls back
TracesOpenTelemetry, TempoWhere one request spent its time: SQL, Redis, the OpenAI call
Logsstructlog JSON, LokiWhat happened, with the request id and trace id on every line
LLM tracesLangfusePrompts, completions, tokens, cost, and evaluation scores

The app speaks one protocol (OTLP) to one place, the OpenTelemetry Collector, which forwards traces to Tempo and ships the log files to Loki. Backends can change without touching the app. Langfuse shares the app's tracing setup but receives only LLM spans, so its views stay about prompts and answers while Tempo sees the whole request.

The ids tie it together. A user reports a problem with the X-Request-ID from a response; that finds the log lines, the log lines carry the trace_id, and Grafana opens the trace from there.

Building your own

Add request ids and structured JSON logs on day one; they cost nothing and every later tool builds on them. Add tracing when requests start crossing more than two services, and LLM tracing as soon as prompts change more than once a week.

Operations

Running it: processes, schema, health

  • Async all the way down. The database driver, Redis client and OpenAI client are all async, so one worker can hold many conversations while each waits seconds on a model.
  • Several workers per container. WEB_CONCURRENCY sets the count. Anything kept per process must be merged or moved: metrics are merged across workers through PROMETHEUS_MULTIPROC_DIR, and limits live in Redis.
  • Schema as code. Alembic migrations are versioned in git and applied when the container starts; the app never creates tables itself.
  • Two health probes. /health/live says the process answers; /health/ready checks Postgres (required, 503 when down) and Redis (optional, reported as degraded). Orchestrators restart on the first and route traffic on the second.
  • Reproducible images. The Dockerfile installs exactly what uv.lock pins, in a build stage, and runs as a non-root user without compilers.
  • Configuration by environment. One settings object reads environment variables, with per-environment defaults for development, staging, production and test.
Building your own

Run two workers locally as early as possible: it is the cheapest way to find state that should have been shared. Separate liveness from readiness before your first deployment, not after the first outage.

Quality

Evaluation: grading production traces offline

Quality is measured outside the request path. make eval pages through the last day of unscored traces in Langfuse, asks a judge model to score each one against five rubric prompts (structured output: a score from 0 to 1 and a one-sentence reason), and writes the scores back to the traces, where they can be charted over time. Running offline adds no latency or cost to users and lets you re-grade old traces with a new rubric.

Rubrics point different ways: for hallucination and toxicity a high score is bad. The report marks each metric's direction so averages aren't misread.

Building your own

Grade real traffic, and also keep a fixed set of test conversations to run before each prompt or model change. Judge models drift too: re-check a sample of their scores by hand.

Your turn

Build your own, in this order

Each step is usable on its own and gives the next one something to stand on.

  1. Settings and structured logs with a request id per request. Verify: every log line of a request shares one id.
  2. Data layer with migrations: users and sessions. Verify: a fresh database comes up from alembic upgrade head.
  3. Authentication with user and session tokens. Verify: a user token can't reach chat routes.
  4. The agent loop with a persistent checkpointer and a blocking endpoint. Verify: a second message sees the first.
  5. The model layer with an error policy. Verify: a simulated 429 falls back, a 400 does not.
  6. Streaming. Verify: tool output never appears in the stream.
  7. Shared rate limits in Redis. Verify: two workers enforce one limit.
  8. Long-term memory. Verify: a fact from one session is recalled in another.
  9. Metrics, traces and LLM traces. Verify: one request id leads to its logs and its trace.
  10. Offline evaluation. Verify: scores appear on yesterday's traces.
  11. Containers, health probes and CI. Verify: the stack starts from a clean checkout with only secrets provided.

The source for each step is linked from the matching blocks above, and the test suite in tests/ shows how each behavior is checked without running the infrastructure.
