Architecture stress testing

Everything built so far is a claim. The pool is bounded, the fallback rotates, the metrics are honest — but none of that is known until 1,500 users arrive at once. This page runs the load test, then reads the damage in Prometheus and Langfuse.

The problem it solves

A notebook runs one query at a time. Production runs hundreds. Concurrency does not degrade a system gradually — it finds the one bounded resource you did not think about and pins it. Three specific collapse modes:

  • Connection pool exhaustion. Requests queue on QueuePool.connect(), p95 explodes, and the database looks idle the entire time. (Layer 04.)
  • Rate-limit collisions. Your provider's tokens-per-minute quota is shared across all in-flight requests. At high concurrency, everyone hits it simultaneously.
  • Latency amplification. Retries with exponential backoff make a bad minute worse: every retry is another request against an already-saturated provider.

The test rig

A laptop is the wrong load generator — its NIC, its CPU and its home connection become the bottleneck, and you end up measuring your own wifi. The write-up uses an AWS m6i.xlarge (4 vCPU, 16 GiB), about $0.192/hour. An hour of that is cheap insurance.

Testing in development mode changes the result

apply_environment_settings() relaxes the default rate limits in development (1000/day vs 200/day) and sets LOG_LEVEL=DEBUG, which means far more log I/O per request. The run below is therefore optimistic on limits and pessimistic on logging overhead. Fine for shaking out the wiring; re-run against a production profile before you quote the numbers to anyone.

The load script

This is not a health-check ping. Each simulated user performs the full flow — login, session creation, then a chat request that runs the graph, hits Postgres and calls the LLM. 

import asyncio, aiohttp, time

BASE_URL = "http://<instance-ip>:8000/api/v1"
CONCURRENT_USERS = 1500


async def simulate_user(session: aiohttp.ClientSession, user_id: int):
    """Login → create session → chat. The whole user journey, not one endpoint."""
    try:
        # 1. Login (form-encoded, OAuth2 password flow)
        login_data = {"username": f"user{user_id}@test.com",
                      "password": "StrongPassword123!", "grant_type": "password"}
        async with session.post(f"{BASE_URL}/auth/login", data=login_data) as resp:
            if resp.status != 200:
                return False
            token = (await resp.json())["access_token"]

        headers = {"Authorization": f"Bearer {token}"}

        # 2. Create a chat session — returns its OWN token
        async with session.post(f"{BASE_URL}/auth/session", headers=headers) as resp:
            session_token = (await resp.json())["token"]

        session_headers = {"Authorization": f"Bearer {session_token}"}

        # 3. The expensive one: full graph execution
        payload = {"messages": [{"role": "user",
                                 "content": "Explain quantum computing briefly."}]}
        start = time.time()
        async with session.post(f"{BASE_URL}/chatbot/chat",
                                json=payload, headers=session_headers) as resp:
            return {"status": resp.status, "duration": time.time() - start,
                    "user_id": user_id}

    except Exception as e:
        return {"status": "error", "error": str(e)}


async def run_stress_test():
    print(f"🚀 Starting stress test with {CONCURRENT_USERS} users...")
    async with aiohttp.ClientSession() as session:
        tasks = [simulate_user(session, i) for i in range(CONCURRENT_USERS)]
        results = await asyncio.gather(*tasks)
    print("✅ Test Completed. Analyzing results...")


if __name__ == "__main__":
    asyncio.run(run_stress_test())
This is a thundering herd, not a traffic profile

asyncio.gather over 1,500 tasks fires every request at t=0. Real traffic arrives on a distribution. A spike test is genuinely useful — it finds the ceiling fast — but it is the harshest possible shape, and passing it does not mean you have measured steady-state behaviour. The ramp and soak variants below tell you different things.

That WARNING line is the whole point of layer 04

switching_model_fallback old_index=0 new_model=gpt-4o-mini. The provider rate-limited the primary model, tenacity exhausted its retries, and LLMService rotated to the next entry in the registry — mid-incident, with no code path aware it happened. Those users got a slower answer instead of a 500. Without that rotation, a chunk of the 98.4% would have been failures.

Read 98.4% carefully

It is a success rate over a single 1,500-request spike, with development-relaxed rate limits, measured by HTTP status only. It says nothing about whether the answers were good — the fallback model may have produced measurably worse output, which is invisible here and visible in layer 09. Availability and quality are separate measurements, and load tests only cover the first.

Querying Prometheus

Logs at this volume are unreadable. The metrics from layer 07 answer aggregate questions directly:

import requests

PROMETHEUS_URL = "http://<instance-ip>:9090"

# rate() = per-second average over the window. NEVER read a counter raw —
# it resets on restart, and the absolute number is meaningless anyway.
query = 'rate(http_requests_total[5m])'
response = requests.get(f"{PROMETHEUS_URL}/api/v1/query", params={'query': query})

print("📊 Prometheus Metrics:")
for result in response.json()['data']['result']:
    endpoint = result['metric'].get('endpoint', 'unknown')
    value = float(result['value'][1])
    if value > 0:
        print(f"Endpoint: {endpoint} | RPS: {value:.2f}")

Prometheus Metrics:

Endpoint: /api/v1/auth/login    | RPS: 245.50
Endpoint: /api/v1/chatbot/chat  | RPS: 180.20
Endpoint: /api/v1/auth/session  | RPS: 210.15

The ratios are the tell: login > session > chat. Each stage sheds a little traffic — some logins failed, some sessions never got used. In a healthy run all three would be near-equal, since every simulated user performs all three steps. The gap is where users dropped out.

Checking Langfuse

Prometheus proves requests were served. It cannot tell you whether the agent was thinking or just erroring out fast. Traces carry per-run latency and cost: 

from langfuse import Langfuse
langfuse = Langfuse()

traces = langfuse.get_traces(limit=5)

print("\n🧠 Langfuse Traces (Recent):")
for trace in traces.data:
    print(f"Trace ID: {trace.id} | Latency: {trace.latency}s | Cost: ${trace.total_cost:.5f}")

Latency spread from 0.98s to 2.10s across five traces, and cost varying nearly 3× — different models handled different requests, which is the fallback rotation showing up in the billing data. That per-request cost is the number your unit economics rest on: at $0.0003 a turn, 10,000 users averaging 20 turns a day is roughly $60/day in inference alone, before you count the memory-extraction call that fires after every response.

Beyond the spike test

TestShapeWhat only it finds
SpikeAll users at t=0Hard ceilings: pool size, provider quota, accept queue
RampLinear increase over minutesThe knee — the exact concurrency where latency turns non-linear
SoakModerate load for hoursMemory leaks, connection leaks, unbounded caches, disk-full from logs
ChaosKill the DB mid-runWhether pool_pre_ping and the degraded-start paths actually work
The soak test is the one people skip

A spike test that passes in 90 seconds cannot reveal a connection leaked once per exception. Run moderate load for four hours and watch db_connections — which, as noted on page 07, this codebase declares but never populates. Wiring that gauge up is a prerequisite for the soak test to tell you anything.

Where this leaves you

Ten layers: a modular codebase with environment-aware settings, a typed persistence layer, guards at the perimeter, services that absorb dependency failure, a stateful agent with two kinds of memory, a streaming API, three signals of observability, reproducible builds, continuous evaluation, and evidence that it holds under load.

None of it is exotic. It is the ordinary discipline of running software, applied to a component that is non-deterministic, slow and metered — which is exactly why the discipline matters more here, not less. The gaps flagged along the way (a real circuit breaker, the unwired db_connections gauge, tests in CI, immutable image tags, multi-stage builds, bounded tool loops) are the honest next commits.
