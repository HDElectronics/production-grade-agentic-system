DevOps automation

How the thing gets built, how it refuses to start when misconfigured, how its dashboards exist without anyone clicking, and how a push to master becomes an image. Three questions: how do we deploy it, how do we watch it, how do we know the environment is ready.

The Dockerfile

FROM python:3.13.2-slim

WORKDIR /app

ARG APP_ENV=production

ENV APP_ENV=${APP_ENV} \
    PYTHONFAULTHANDLER=1 \        # dump a traceback on a hard crash / SIGSEGV
    PYTHONUNBUFFERED=1 \          # don't buffer stdout — logs appear in real time
    PYTHONHASHSEED=random \       # per-process hash randomisation
    PIP_NO_CACHE_DIR=1 \          # no wheel cache = smaller image
    PIP_DISABLE_PIP_VERSION_CHECK=on \
    PIP_DEFAULT_TIMEOUT=100

# libpq-dev + build-essential are needed to compile psycopg2.
# Chained into one RUN so the apt lists deletion lands in the SAME layer —
# a separate RUN rm would leave the lists in the previous layer forever.
RUN apt-get update && apt-get install -y \
    build-essential \
    libpq-dev \
    && pip install --upgrade pip \
    && pip install uv \
    && rm -rf /var/lib/apt/lists/*

# THE CACHE TRICK: dependency manifest first, source code later.
COPY pyproject.toml .
RUN uv venv && . .venv/bin/activate && uv pip install -e .

COPY . .                                     # source changes invalidate only from here

RUN chmod +x /app/scripts/docker-entrypoint.sh

# Root inside a container is root on the host if anything escapes.
RUN useradd -m appuser && chown -R appuser:appuser /app
USER appuser

RUN mkdir -p /app/logs
EXPOSE 8000

ENTRYPOINT ["/app/scripts/docker-entrypoint.sh"]   # always runs — the gatekeeper
CMD ["/app/.venv/bin/uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
ENTRYPOINT vs CMD

ENTRYPOINT is the program; CMD is its default arguments. Running docker run image bash replaces the CMD but the entrypoint still executes — so the secret validation below cannot be skipped by passing a different command. That is exactly why the check lives there rather than in Python.

Two things worth fixing before this is genuinely production-grade

Not multi-stage. build-essential stays in the final image — hundreds of megabytes of compiler shipped to production and a wider attack surface. A builder stage that copies only .venv forward would cut the image substantially. No HEALTHCHECK instruction. The compose file defines one, so plain docker run has no health signal at all.

Fail fast on missing secrets

The worst deployment failure is the one that half-works: the container starts, serves /health, and 500s on every real request because OPENAI_API_KEY was empty. The entrypoint refuses to start rather than start broken. 

#!/bin/bash
set -e                       # abort on any error — no silent partial startup

# Runtime secret injection: the .env file is mounted, not baked into the image
if [ -f ".env.${APP_ENV}" ]; then
    echo "Loading environment from .env.${APP_ENV}"
    # (source the file …)
fi

# Fail fast on anything the app cannot run without
required_vars=("JWT_SECRET_KEY" "OPENAI_API_KEY")
missing_vars=()

for var in "${required_vars[@]}"; do
    if [[ -z "${!var}" ]]; then          # ${!var} = indirect expansion
        missing_vars+=("$var")
    fi
done

if [[ ${#missing_vars[@]} -gt 0 ]]; then
    echo "ERROR: The following required environment variables are missing:"
    for var in "${missing_vars[@]}"; do
        echo "  - $var"
    done
    exit 1                    # container exits non-zero: the orchestrator sees it
fi

exec "$@"                     # hand off to CMD, replacing this shell as PID 1
exec "$@" is doing more than it looks

Without exec, bash stays PID 1 and uvicorn becomes its child — so docker stop's SIGTERM goes to bash, which does not forward it, and Docker kills the container after the 10-second grace period. In-flight streams get severed and the lifespan shutdown never runs, so langfuse.flush() is skipped. exec replaces the shell, uvicorn becomes PID 1, and graceful shutdown works.

Prometheus pulls. That means it also knows when a target stops answering — the synthetic up metric goes to 0 — so "the app is down" is a query, not a missing signal. A push-based system cannot tell silence from health.

Dashboards as code

The JSON in grafana/dashboards/json/ is version-controlled, so a fresh Grafana container comes up with your charts already there. The tension: editable: true lets people tweak in the UI, and those tweaks are lost on the next container restart. Either export back to the repo after editing, or set editable: false and make the repo the only path.

The Makefile as an interface

Nobody should have to remember APP_ENV=production docker-compose --env-file .env.production up -d --build db app. The Makefile is the contract between the codebase and the humans operating it. 

install:
	pip install uv
	uv sync

# Local development with hot reload on uvloop
dev:
	@echo "Starting server in development environment"
	@bash -c "source scripts/set_env.sh development && \
	  uv run uvicorn app.main:app --reload --port 8000 --loop uvloop"

# Full stack in Docker, environment-parameterised
docker-run-env:
	@if [ -z "$(ENV)" ]; then \
	  echo "ENV is not set. Usage: make docker-run-env ENV=development"; \
	  exit 1; \
	fi
	@ENV_FILE=.env.$(ENV); \
	APP_ENV=$(ENV) docker-compose --env-file $$ENV_FILE up -d --build db app

# Run the LLM-as-a-judge evaluation suite
eval:
	@echo "Running evaluation with interactive mode"
	@bash -c "source scripts/set_env.sh ${ENV:-development} && \
	  python -m evals.main --interactive"

The ENV guard is not decoration

Without if [ -z "$(ENV)" ], running make docker-run-env bare would expand to --env-file .env. — a file that does not exist — and compose would start with an empty environment. Every secret blank, the app crash-looping, and a confusing error three layers down. Guarding required variables in the target is a one-line fix for a ten-minute debugging session.

Continuous delivery

name: Build and push to Docker Hub

on:
  push:
    branches:
      - master

jobs:
  build-and-push:
    name: Build and push to Docker Hub
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v3

      - name: Build Image
        run: |
          make docker-build-env ENV=production          # same Makefile as local
          docker tag fastapi-langgraph-template:production \
            ${{ secrets.DOCKER_USERNAME }}/my-agent:production

      - name: Log in to Docker Hub
        run: |
          echo ${{ secrets.DOCKER_PASSWORD }} | \
            docker login --username ${{ secrets.DOCKER_USERNAME }} --password-stdin

      - name: Push Image
        run: docker push ${{ secrets.DOCKER_USERNAME }}/my-agent:production

CI calling make docker-build-env — the same target a developer runs locally — is the detail that matters. When the build is defined once, "works locally, fails in CI" becomes a much smaller category of bug.

Three gaps in this pipeline

No tests run before the push. A commit that fails pytest still ships an image. Only the :production tag. Every build overwrites it, so there is no immutable reference to roll back to — tag with the commit SHA as well. A long-lived Docker Hub password in secrets. OIDC federation or a scoped access token limits the damage if the repository is compromised.
