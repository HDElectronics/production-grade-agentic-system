Layer 09 · Operations

Evaluation framework

Unit tests are deterministic; agents are not. The same prompt, the same input, a different answer — and a system-prompt tweak that fixes one case quietly breaks five others. This layer grades real production traces with an LLM judge and writes the scores back, so quality becomes a trend line instead of a vibe.

The problem it solves

You cannot assert response == expected against a generative model. But you also cannot ship prompt changes on hope. What you can do is score a sample of real traffic against explicit rubrics and watch the aggregate move.

The framework here has four moving parts:

  1. A structured output schema so the judge must produce a number and a justification.
  2. A rubric per metric, stored as Markdown, discovered automatically.
  3. An evaluator that pulls traces from Langfuse and grades them.
  4. A CLI so it runs from a terminal or a cron job.

Forcing the judge to show its work

from pydantic import BaseModel, Field


class ScoreSchema(BaseModel):
    """Structured output for the LLM judge."""

    score: float = Field(description="provide a score between 0 and 1")
    reasoning: str = Field(description="provide a one sentence reasoning")

Two fields, both load-bearing:

  • score is aggregatable. "The response was pretty good" cannot be charted; 0.82 can.
  • reasoning makes a bad grade auditable. When hallucination spikes on Tuesday you need to read why the judge thought so — often the judge was wrong, and you have just learned your rubric is ambiguous.
Reasoning before score, not after

The rubrics all end with "Think step by step. Provide a reasoning before the score." Field order in the schema matters for the same reason: a model that emits the number first has committed before it reasons, and the reasoning becomes a post-hoc justification. Ordering the output so the argument precedes the verdict measurably improves grading consistency.

Rubrics as content

Five metrics ship in evals/metrics/prompts/. Each one is a Markdown file — no Python, no redeploy to change a grading standard. 

conciseness.md      # is it padded with filler?
hallucination.md    # did it make things up?
helpfulness.md      # would this actually help the user?
relevancy.md        # did it answer the question that was asked?
toxicity.md         # is it safe to send?

## Scoring Criteria
A generation can be considered to hallucinate (Score: 1) if it:
- Does not align with established knowledge
- Contradicts verifiable data
- Fails to follow logical inference
- Includes elements that are implausible, misleading, or entirely fictional

The polarity trap

For hallucination and toxicity, 1 is bad. For relevancy, helpfulness and conciseness, 1 is good. Both directions are stored in the same score field with no polarity flag, so a dashboard that averages all five metrics into one "quality score" produces a number that means nothing. Chart them separately, or normalise the direction before aggregating.

The stronger rubrics include a worked example — a few-shot anchor that pins the scale:

Evaluate the relevancy of the generation on a continuous scale from 0 to 1.

## Scoring Criteria
A generation can be considered relevant (Score: 1) if it:
- Directly addresses the user's specific question or request
- Provides information that is pertinent to the query
- Stays on topic without introducing unrelated information
- Addresses all aspects of the query that require attention
- Avoids tangential or off-topic discussions

Discovery is automatic — dropping a new .md file in the folder adds a metric:

import os

metrics = []
PROMPTS_DIR = os.path.join(os.path.dirname(__file__), "prompts")

for file in os.listdir(PROMPTS_DIR):
    if file.endswith(".md"):
        metrics.append({
            "name": file.replace(".md", ""),
            "prompt": open(os.path.join(PROMPTS_DIR, file), "r").read(),
        })
Convenient, and slightly dangerous

os.listdir returns entries in arbitrary order, so metric order is not stable across machines — fine for a dict, confusing in a report. The file handles are never closed. And a stray notes.md in that folder silently becomes a grading metric that runs against every trace, on your budget. A sorted(glob("*.md")) with a context manager costs nothing and removes all three.

The evaluator

Fetch traces → for each trace, for each metric, call the judge → push the score back onto the trace.

class Evaluator:
    """Automated judge that grades real production interactions."""

    def __init__(self):
        self.client = openai.AsyncOpenAI(api_key=settings.OPENAI_API_KEY)
        self.langfuse = Langfuse(public_key=settings.LANGFUSE_PUBLIC_KEY,
                                 secret_key=settings.LANGFUSE_SECRET_KEY)

    async def run(self, generate_report_file=True):
        # 1. Real traffic, not a synthetic test set. This is the whole point:
        #    you are measuring what users actually did.
        traces = self.__fetch_traces()
        logger.info(f"Found {len(traces)} traces to evaluate")

        for trace in tqdm(traces, desc="Evaluating traces"):
            input_text, output_text = get_input_output(trace)

            # 2. Every metric against every trace
            for metric in metrics:
                score = await self._run_metric_evaluation(metric, input_text, output_text)
                if score:
                    # 3. Attach the grade to the trace it came from
                    self._push_to_langfuse(trace, score, metric)

    async def _run_metric_evaluation(self, metric: dict, input: str,
                                     output: str) -> ScoreSchema | None:
        try:
            response = await self.client.beta.chat.completions.parse(
                model="gpt-4o",              # judge with a STRONG model, always
                messages=[
                    {"role": "system", "content": metric["prompt"]},   # the rubric
                    {"role": "user",
                     "content": f"Input: {input}\nGeneration: {output}"},
                ],
                response_format=ScoreSchema,  # provider-enforced structured output
            )
            return response.choices[0].message.parsed
        except Exception as e:
            # One metric failing must not abandon the whole run
            logger.error(f"Metric {metric['name']} failed", error=str(e))
            return None

    def _push_to_langfuse(self, trace: TraceWithDetails, score: ScoreSchema, metric: dict):
        """Persist the grade so you can chart 'hallucination over 30 days'."""
        self.langfuse.create_score(
            trace_id=trace.id,
            name=metric["name"],
            value=score.score,
            comment=score.reasoning,      # the audit trail
        )
Judge with a stronger model than you serve with

The agent runs gpt-5-mini; the judge runs gpt-4o. Grading is a harder task than answering — it requires holding the rubric, the input and the output in mind simultaneously. Using the same model to judge itself also imports its own blind spots: a model that hallucinated a fact will often fail to notice that fact is wrong.

The cost multiplier nobody budgets for

5 metrics × every trace × a frontier model. Grading is not free and it is not cheap — evaluating every trace can cost more than serving the traffic did, since each judge call re-reads the whole input and output. Sample. 200 traces a day at random gives you a trend line with tight enough confidence, at 2% of the cost of grading everything.

The loop is sequential

for trace: for metric: await … makes N×M round trips one at a time. With 500 traces and 5 metrics that is 2,500 sequential calls — hours. asyncio.gather with a semaphore would cut it to minutes; the client is already async, so nothing but the loop shape is stopping it.

The entry point

async def run_evaluation(generate_report: bool = True) -> None:
    """CLI command. Usage: python -m evals.main"""
    print("Starting AI Evaluation...")
    try:
        evaluator = Evaluator()
        await evaluator.run()
        print("✅ Evaluation completed successfully.")
    except Exception as e:
        logger.error("Evaluation failed", error=str(e))
        sys.exit(1)          # non-zero: a CI job or cron will notice


if __name__ == "__main__":
    asyncio.run(run_evaluation())

evals/main.py also ships an interactive mode (make eval), a quick mode over a shorter trace window, and a report generator that aggregates per-metric averages into a summary — which is what turns a pile of scores into something you can put in a pull request.

The feedback loop this creates

Regression detection 30-day trend
This is the difference between a project and a platform

A prompt change ships on Tuesday. Wednesday's eval run scores the traces it produced. Thursday morning the hallucination line has moved and you know which commit to look at — before enough users noticed to complain. Without it, quality regressions are discovered by customers, and the cause is three weeks of commits ago.

What LLM-as-a-judge cannot do

  • It is not ground truth. The judge is another probabilistic model with its own biases — notably a preference for longer, more confident-sounding answers. Calibrate it against human labels on a small set before you trust the absolute numbers.
  • Absolute scores drift; deltas hold. "Hallucination is 0.12" means little on its own. "Hallucination went from 0.08 to 0.19 after Tuesday's deploy" is actionable. Never compare scores across judge-model versions.
  • It cannot see what the trace omits. Judging input and output alone misses whether the right tool was called, whether retrieved memory was correct, or whether the answer was slow. Those need their own checks.
  • It does not replace tests. The deterministic parts of the system — auth, schemas, routing, sanitisation — still deserve ordinary pytest. Do not let a fashionable eval suite become an excuse for an untested API.
