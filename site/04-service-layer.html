Layer 04 · Core

The service layer

Routes should be boring. Everything that can fail under load — the database connection, the LLM provider — is wrapped in a service that owns the failure: a bounded connection pool, exponential-backoff retries, and circular fallback across models. This is the layer that decides whether an outage is a blip or an incident.

The problem it solves

Two external dependencies dominate an agent's runtime, and neither is reliable at the moment you need it. Postgres will refuse connections past max_connections; the LLM provider will rate-limit you, time out, or return 500s in bursts. Handling either inside a route handler means duplicating the logic in every route and getting it subtly wrong in most of them.

So both live behind singletons: database_service and llm_service.

Connection pooling

Opening a Postgres connection costs a TCP handshake, TLS, and authentication — tens of milliseconds before your query runs. At one connection per request, that overhead dominates, and at a few hundred concurrent requests the database refuses new connections entirely. A pool keeps a fixed set open and hands them out. 

from sqlalchemy.pool import QueuePool
from sqlmodel import Session, SQLModel, create_engine, select


class DatabaseService:
    """Singleton owning the connection pool and all CRUD."""

    def __init__(self):
        try:
            connection_url = (
                f"postgresql://{settings.POSTGRES_USER}:{settings.POSTGRES_PASSWORD}"
                f"@{settings.POSTGRES_HOST}:{settings.POSTGRES_PORT}/{settings.POSTGRES_DB}"
            )

            self.engine = create_engine(
                connection_url,
                poolclass=QueuePool,
                pool_size=settings.POSTGRES_POOL_SIZE,        # kept open permanently
                max_overflow=settings.POSTGRES_MAX_OVERFLOW,  # temporary burst headroom
                pool_pre_ping=True,   # SELECT 1 before handing a connection out
                pool_timeout=30,      # give up waiting after 30s -> TimeoutError
                pool_recycle=1800,    # drop connections older than 30 min
            )

            # Code-first schema creation. Fine at this scale; graduate to
            # Alembic the moment you need a non-destructive column change.
            SQLModel.metadata.create_all(self.engine)
            logger.info("database_initialized", pool_size=settings.POSTGRES_POOL_SIZE)

        except SQLAlchemyError as e:
            logger.error("database_initialization_failed", error=str(e))
            # Dev should crash loudly. Production may prefer to start
            # degraded and let the healthcheck report it.
            if settings.ENVIRONMENT != Environment.PRODUCTION:
                raise


database_service = DatabaseService()      # one pool per process

The four parameters that matter

pool_size
Steady-state connections held open. Total across your fleet must stay under Postgres max_connections — with 4 workers and pool_size=20 you are already at 80 before overflow.
max_overflow
Extra connections allowed during a spike, closed again when returned. Burst capacity without paying for it permanently.
pool_pre_ping
Cheap liveness check before reuse. Without it, the first request after an idle period fails with a broken pipe — because a firewall or the database silently dropped the socket.
pool_recycle
Proactively closes connections older than 30 minutes. Managed Postgres (RDS, Cloud SQL) and load balancers cut idle connections on their own schedule; recycling first means you never notice.
The arithmetic that bites people

Max concurrent DB work per process is pool_size + max_overflow. Request 21 with pool_size=20, max_overflow=10 does not fail — it waits, up to pool_timeout seconds. That latency shows up as a p99 spike with no slow query to blame, which is one of the harder things to diagnose from a dashboard. The pool exhaustion is upstream of the symptom.

CRUD stays thin

async def get_user_by_email(self, email: str) -> Optional[User]:
    # The context manager returns the connection to the pool on exit,
    # including when the body raises. Forgetting this is how pools leak.
    with Session(self.engine) as session:
        statement = select(User).where(User.email == email)
        return session.exec(statement).first()


async def create_session(self, session_id: str, user_id: int, name: str = "") -> ChatSession:
    with Session(self.engine) as session:
        chat_session = ChatSession(id=session_id, user_id=user_id, name=name)
        session.add(chat_session)
        session.commit()
        session.refresh(chat_session)     # pull DB-assigned defaults back
        return chat_session


async def health_check(self) -> bool:
    """Used by /health, which Docker and Kubernetes poll."""
    try:
        with Session(self.engine) as session:
            session.exec(select(1))
        return True
    except Exception as e:
        logger.error("database_health_check_failed", error=str(e))
        return False
A deliberate wart worth knowing about

These methods are async def but call the synchronous SQLModel API, so each one blocks the event loop for the duration of its query. At this scale the queries are indexed point-lookups and it does not matter. It would matter under heavy load or with slow queries — the fix is AsyncSession with an async driver (asyncpg), or offloading to a thread pool. Worth knowing before you copy the pattern into something hotter.

The LLM registry

Models are pre-instantiated once and looked up by name, so switching "brains" mid-request costs nothing. Note the production-only sampling parameters — the same registry behaves differently per environment. 

class LLMRegistry:
    """Ordered registry — the order IS the fallback chain."""

    LLMS: List[Dict[str, Any]] = [
        {"name": "gpt-5-mini", "llm": ChatOpenAI(
            model="gpt-5-mini", api_key=settings.OPENAI_API_KEY,
            max_tokens=settings.MAX_TOKENS,
            reasoning={"effort": "low"})},

        {"name": "gpt-5", "llm": ChatOpenAI(
            model="gpt-5", api_key=settings.OPENAI_API_KEY,
            max_tokens=settings.MAX_TOKENS,
            reasoning={"effort": "medium"})},

        {"name": "gpt-5-nano", "llm": ChatOpenAI(
            model="gpt-5-nano", api_key=settings.OPENAI_API_KEY,
            max_tokens=settings.MAX_TOKENS,
            reasoning={"effort": "minimal"})},

        {"name": "gpt-4o", "llm": ChatOpenAI(
            model="gpt-4o", temperature=settings.DEFAULT_LLM_TEMPERATURE,
            api_key=settings.OPENAI_API_KEY, max_tokens=settings.MAX_TOKENS,
            # Tighter sampling in production, looser locally for exploration
            top_p=0.95 if settings.ENVIRONMENT == Environment.PRODUCTION else 0.8,
            presence_penalty=0.1 if settings.ENVIRONMENT == Environment.PRODUCTION else 0.0,
            frequency_penalty=0.1 if settings.ENVIRONMENT == Environment.PRODUCTION else 0.0)},

        {"name": "gpt-4o-mini", "llm": ChatOpenAI(
            model="gpt-4o-mini", temperature=settings.DEFAULT_LLM_TEMPERATURE,
            api_key=settings.OPENAI_API_KEY, max_tokens=settings.MAX_TOKENS)},
    ]

    @classmethod
    def get(cls, model_name: str) -> BaseChatModel:
        for entry in cls.LLMS:
            if entry["name"] == model_name:
                return entry["llm"]
        return cls.LLMS[0]["llm"]          # unknown name -> first entry

    @classmethod
    def get_all_names(cls) -> List[str]:
        return [entry["name"] for entry in cls.LLMS]
Order the registry by capability, not by cost

Fallback rotates forward through this list. Put a model you'd be happy to serve next in line — if your fallback is dramatically weaker, a provider blip silently degrades answer quality instead of producing an error you'd notice. Quality regressions are much harder to detect than 500s, which is precisely why layer 09 exists.

Retries and circular fallback

Two nested strategies. Retry handles a bad second; fallback handles a bad hour.

class LLMService:
    def __init__(self):
        self._llm: Optional[BaseChatModel] = None
        self._current_model_index: int = 0
        try:
            self._llm = LLMRegistry.get(settings.DEFAULT_LLM_MODEL)
            self._current_model_index = LLMRegistry.get_all_names().index(
                settings.DEFAULT_LLM_MODEL)
        except ValueError:
            self._llm = LLMRegistry.LLMS[0]["llm"]

    def _switch_to_next_model(self) -> bool:
        """Circular: the last entry wraps around to the first."""
        try:
            next_index = (self._current_model_index + 1) % len(LLMRegistry.LLMS)
            next_model_entry = LLMRegistry.LLMS[next_index]
            logger.warning("switching_model_fallback",
                           old_index=self._current_model_index,
                           new_model=next_model_entry["name"])
            self._current_model_index = next_index
            self._llm = next_model_entry["llm"]
            return True
        except Exception as e:
            logger.error("model_switch_failed", error=str(e))
            return False

    @retry(
        stop=stop_after_attempt(settings.MAX_LLM_CALL_RETRIES),   # 3 attempts
        wait=wait_exponential(multiplier=1, min=2, max=10),       # 2s, 4s, 8s (capped)
        # Only retry what a retry can actually fix. A 400 for a malformed
        # request will fail identically every time — retrying it just
        # multiplies the latency before the user sees the error.
        retry=retry_if_exception_type((RateLimitError, APITimeoutError, APIError)),
        before_sleep=before_sleep_log(logger, "WARNING"),
        reraise=True,
    )
    async def _call_with_retry(self, messages: List[BaseMessage]) -> BaseMessage:
        if not self._llm:
            raise RuntimeError("LLM not initialized")
        return await self._llm.ainvoke(messages)

    async def call(self, messages: List[BaseMessage]) -> BaseMessage:
        """Retry loop wrapped in a fallback loop."""
        total_models = len(LLMRegistry.LLMS)
        models_tried = 0

        while models_tried < total_models:
            try:
                return await self._call_with_retry(messages)
            except OpenAIError as e:
                models_tried += 1
                logger.error("model_failed_exhausted_retries",
                             model=LLMRegistry.LLMS[self._current_model_index]["name"],
                             error=str(e))
                if models_tried >= total_models:
                    break
                self._switch_to_next_model()

        raise RuntimeError("Failed to get response from any LLM after exhausting all options.")

    def bind_tools(self, tools: List) -> "LLMService":
        if self._llm:
            self._llm = self._llm.bind_tools(tools)
        return self


llm_service = LLMService()
Worst-case latency is a multiplication, not an addition

3 attempts × (2s + 4s + 8s of backoff) × 5 models is well over a minute of waiting before call() finally raises. Your HTTP timeout, your reverse proxy's timeout and your client's timeout will all fire long before that. Retries buy availability by spending latency — budget it explicitly, and cap total attempts against your actual request deadline.

Circuit breaking — what is here and what is not

The rotation above is the load-shedding piece: a model that has failed is abandoned for the current request and the service moves on. But the switch is sticky, not self-healing. _current_model_index stays where it landed, so after an incident every subsequent request is served by whatever model happened to be next in line — until a future failure rotates again, eventually wrapping back around.

A real circuit breaker adds two things this does not have

Per-model failure state: mark a model open after N consecutive failures and skip it entirely for a cooldown, instead of re-paying its retry budget on the next request. Half-open probing: after the cooldown, let a single request through; promote back to healthy on success, re-open on failure. Without those, a hard provider outage costs every request the full retry ladder before it can fall back. Worth adding if your primary model matters for quality — see the latency arithmetic above.
