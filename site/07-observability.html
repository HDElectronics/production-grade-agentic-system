Layer 07 · Operations

Observability & operational wiring

Metrics tell you that something is wrong. Logs tell you which request. Traces tell you where inside the agent. This page builds all three, plus the main.py wiring that puts them in the right order — because middleware order is not a style choice.

The problem it solves

At 10,000 users you cannot read the logs. "Error processing request" tells you nothing: which request, which user, which model, how long had it been running. And nobody will notice p95 latency doubling until it triples and someone complains.

Three signals, three jobs:

Metrics
Cheap, aggregate, always on. Answers "is it slow, and since when".
Logs
Per-event, high cardinality. Answers "what happened to user 452 at 10:46:22".
Traces
Per-run causal tree. Answers "which node in the graph burned six seconds".

Defining the metrics

from prometheus_client import Counter, Histogram, Gauge
from starlette_prometheus import metrics, PrometheusMiddleware

# ---- 1. HTTP ----
http_requests_total = Counter(
    "http_requests_total", "Total number of HTTP requests",
    ["method", "endpoint", "status"])          # labels = the dimensions you can slice by

http_request_duration_seconds = Histogram(
    "http_request_duration_seconds", "HTTP request duration in seconds",
    ["method", "endpoint"])                    # default buckets: .005 … 10s

# ---- 2. Infrastructure ----
db_connections = Gauge("db_connections", "Number of active database connections")

# ---- 3. AI-specific ----
# LLM calls are seconds, not milliseconds — the default buckets would put
# nearly every sample in +Inf and make percentiles meaningless.
llm_inference_duration_seconds = Histogram(
    "llm_inference_duration_seconds", "Time spent processing LLM inference",
    ["model"], buckets=[0.1, 0.3, 0.5, 1.0, 2.0, 5.0])

llm_stream_duration_seconds = Histogram(
    "llm_stream_duration_seconds", "Time spent processing LLM stream inference",
    ["model"], buckets=[0.1, 0.5, 1.0, 2.0, 5.0, 10.0])


def setup_metrics(app):
    app.add_middleware(PrometheusMiddleware)
    app.add_route("/metrics", metrics)         # what Prometheus scrapes every 15s

The three metric types, and when each is wrong

TypeSemanticsUse forGets misused as
CounterOnly goes up; resets on restartRequests, errors, tokensA current value — use rate(), never the raw number
GaugeGoes up and downPool connections, queue depthAnything cumulative
HistogramBucketed distributionLatency, response sizeAn average — the mean hides every user who suffered
Label cardinality is the classic way to take Prometheus down

Every distinct label combination is a separate time series. endpoint is safe because routes are finite. Adding user_id would create one series per user — at 10,000 users, times method, times status, that is millions of series and an out-of-memory kill. High-cardinality identity belongs in logs and traces, never in metric labels.

A real gap in this implementation

db_connections is declared and never set — nothing calls .set() on it, so it reports 0 forever. Given the pool-exhaustion failure mode on page 04, this is the single most valuable metric to actually wire up: engine.pool.checkedout() on a timer would turn an invisible incident into an obvious one.

Middleware

Two classes, one job each: record every request, and make every log line self-describing.

class MetricsMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request: Request, call_next: Callable) -> Response:
        start_time = time.time()
        try:
            response = await call_next(request)
            status_code = response.status_code
            return response
        except Exception:
            status_code = 500        # record the crash, then let it propagate
            raise
        finally:
            # finally: runs on success, on HTTPException, and on crash.
            # Without it your metrics would only describe your happy path.
            duration = time.time() - start_time
            if request.url.path not in ["/metrics", "/health"]:   # drop the noise
                http_requests_total.labels(
                    method=request.method, endpoint=request.url.path,
                    status=status_code).inc()
                http_request_duration_seconds.labels(
                    method=request.method, endpoint=request.url.path).observe(duration)

class LoggingContextMiddleware(BaseHTTPMiddleware):
    """Extract identity BEFORE the router, so auth failures are attributable too."""

    async def dispatch(self, request: Request, call_next: Callable) -> Response:
        try:
            # 1. Context lives in a ContextVar. Workers are reused across
            #    requests, so a stale value would leak into someone else's logs.
            clear_context()

            # 2. Peek at the token WITHOUT verifying it. This value is used
            #    only to tag logs — never to authorise anything.
            auth_header = request.headers.get("authorization")
            if auth_header and auth_header.startswith("Bearer "):
                token = auth_header.split(" ")[1]
                try:
                    payload = jwt.get_unverified_claims(token)
                    if payload.get("sub"):
                        bind_context(subject_id=payload.get("sub"))
                except JWTError:
                    pass          # malformed tokens are the router's problem

            response = await call_next(request)

            if hasattr(request.state, "user_id"):
                bind_context(user_id=request.state.user_id)
            return response
        finally:
            clear_context()       # symmetric cleanup, always
Why an unverified decode is acceptable here — and only here

A forged token can put any sub it likes into your logs. That is a log-poisoning nuisance, not a privilege escalation, because nothing downstream trusts this value: the auth dependency on page 06 verifies independently. The payoff is that a 401 still tells you who tried. Never reuse this pattern for a decision.

Structured logging

structlog emits key-value events instead of prose. In development they render as readable console lines; in production they are JSON that a log aggregator can index and query. 

from contextvars import ContextVar

# ContextVar, not a global: each async task gets its own view, so two
# concurrent requests can never see each other's context.
_request_context: ContextVar[Dict[str, Any]] = ContextVar("request_context", default={})


def bind_context(**kwargs: Any) -> None:
    current = _request_context.get()
    _request_context.set({**current, **kwargs})     # merge, never replace


def clear_context() -> None:
    _request_context.set({})


def add_context_to_event_dict(logger, method_name, event_dict):
    """structlog processor: injects the bound context into every event."""
    event_dict.update(_request_context.get())
    return event_dict

The call site stays trivial — the context arrives on its own:

Event names are identifiers, not sentences

"llm_response_generated" rather than f"Generated response for {user}". Stable snake_case names are groupable — count by (event) works, alerts can key off them, and the variable parts stay in fields where they are queryable. Interpolating values into the message is what makes logs unsearchable at volume.

Wiring it all: src/main.py

The entry point does no business logic. It manages lifecycle, assembles the middleware stack, normalises errors, and mounts the router. 

@asynccontextmanager
async def lifespan(app: FastAPI):
    """Startup and shutdown in one function.

    Replaces @app.on_event, and — unlike it — guarantees the shutdown half
    runs even if startup raised partway through.
    """
    logger.info("application_startup",
                project_name=settings.PROJECT_NAME, version=settings.VERSION,
                api_prefix=settings.API_V1_STR, environment=settings.ENVIRONMENT.value)

    yield                       # the application serves traffic here

    logger.info("application_shutdown")
    langfuse.flush()            # Langfuse buffers spans; without this the
                                # last few seconds of traces are lost on deploy


app = FastAPI(
    title=settings.PROJECT_NAME,
    version=settings.VERSION,
    openapi_url=f"{settings.API_V1_STR}/openapi.json",
    lifespan=lifespan,
)

# ORDER IS SEMANTIC. First added = outermost = sees the request first.
setup_metrics(app)                          # 1. PrometheusMiddleware + /metrics
app.add_middleware(LoggingContextMiddleware)# 2. bind context before anything logs
app.add_middleware(MetricsMiddleware)       # 3. time the inner stack
app.add_middleware(                         # 4. CORS closest to the router
    CORSMiddleware,
    allow_origins=settings.ALLOWED_ORIGINS,
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)

# Rate limiting needs both halves or the decorator raises instead of 429ing
app.state.limiter = limiter
app.add_exception_handler(RateLimitExceeded, _rate_limit_exceeded_handler)
allow_credentials=True with a wildcard origin does not work

ALLOWED_ORIGINS defaults to ["*"]. Browsers refuse credentialed requests against a wildcard Access-Control-Allow-Origin — the spec forbids it — so the combination silently breaks cookie-based clients while looking permissive. List real origins per environment.

Uniform validation errors

@app.exception_handler(RequestValidationError)
async def validation_exception_handler(request: Request, exc: RequestValidationError):
    # warning, not error: a 422 is the client's mistake, and paging
    # someone for it will teach them to ignore the pager.
    logger.warning("validation_error", path=request.url.path, errors=str(exc.errors()))

    formatted_errors = []
    for error in exc.errors():
        # ["body", "messages", 0, "content"] -> "messages -> 0 -> content"
        loc = " -> ".join([str(p) for p in error["loc"] if p != "body"])
        formatted_errors.append({"field": loc, "message": error["msg"]})

    return JSONResponse(status_code=status.HTTP_422_UNPROCESSABLE_ENTITY,
                        content={"detail": "Validation error", "errors": formatted_errors})

Health check that means something

@app.get("/health")
@limiter.limit(settings.RATE_LIMIT_ENDPOINTS["health"][0])
async def health_check(request: Request) -> Dict[str, Any]:
    # A health check that only proves the process is alive is theatre.
    # This one actually round-trips the database.
    db_healthy = await database_service.health_check()

    return JSONResponse(
        status_code=status.HTTP_200_OK if db_healthy else status.HTTP_503_SERVICE_UNAVAILABLE,
        content={
            "status": "healthy" if db_healthy else "degraded",
            "components": {"api": "healthy",
                           "database": "healthy" if db_healthy else "unhealthy"},
            "timestamp": datetime.now().isoformat(),
        })
Liveness vs readiness

This endpoint conflates them. Under Kubernetes, a dependency check on the liveness probe means a brief database blip restarts every pod at once — turning a recoverable incident into an outage. The usual split: liveness = "the process responds" (the cheap /api/v1/health in the router), readiness = "it can serve traffic" (this one, which gates the load balancer without killing anything).

Tracing with Langfuse

Metrics and logs stop at the HTTP boundary. Inside one request the agent may make three LLM calls, two tool calls and a vector search — a tree, not a line. The Langfuse callback records that tree, with per-span latency, token counts and cost. 

config = {
    "configurable": {"thread_id": session_id},
    "callbacks": [CallbackHandler(environment=settings.ENVIRONMENT.value,
                                  user_id=user_id, session_id=session_id)],
    "metadata": {"user_id": user_id, "session_id": session_id,
                 "environment": settings.ENVIRONMENT.value, "debug": settings.DEBUG},
}

Those traces are not just for debugging — they are the input to the evaluation framework in layer 09, which replays them through an LLM judge and writes scores back.
